## 含义说明

`40800` 存储消息的**实际内容主体**，编码为 Protobuf（wire format）。
本列是整张表最核心的字段，文本、图片、文件、语音、位置、合并转发、通话记录等所有消息内容均序列化于此。

# 字段 `40800` — 消息体（共享 Protobuf）

## 速查结论

`40800` 是消息正文和内容元数据的 Protobuf BLOB。C2C 与 group 使用同一套外层结构和消息段模型：

```text
MsgBody.content = 40800 (repeated MsgContent)
```

一行可以包含一个或多个 `MsgContent` 段，因此解析时必须保留段顺序，不能把 repeated 字段压成单个对象。

## 外层和消息段

### `MsgBody`

```protobuf
message MsgBody {
  repeated MsgContent content = 40800;
}
```

顶层通常只有一个 `40800` length-delimited 字段。消息段数量必须按列表处理；C2C 多段消息以两段为主，也存在图文、名片、位置附言和大量复合段。

| `45001` | int64 | 消息段级 ID；不能替代主表 `40001` |

## 解析规则

1. 先按 `MsgBody` 解析顶层 `40800` repeated 字段。
2. 保留每个 `MsgContent` 段及其顺序；不要把 `45001` 当作主表 `40001`。
3. 根据 `45002`、主表 `40011` 和 `40012` 选择字段解释。
4. `45101` 优先按 UTF-8 文本处理；MD5、hash、头像和嵌套 Protobuf 保持 bytes。
5. 未知字段或解析异常使用 `msgdb/proto/wire.py` 的 wire fallback，保留字段号、wire type 和原始 payload。
6. 递归字段（尤其 `47710`）保留树结构；多态 length-delimited 字段不要强行固定为 string 或单一 message。

## 重要边界

- `40011` 是表级外层分类，`45002` 是消息段内容类型；二者有关联，但不是简单复制。
- `45101` 是应用层 UTF-8 文本，不应因偶发 wire-like 字节被识别为 Protobuf。
- `45503`、`45406`、`45862` 等 hash/标识字段必须区分 raw bytes、hex 文本和路径字符串。
- 未在本数据库出现的 content type 或字段只能标记为“无样本”，不能视为不存在。
- 外部资料中的 `48000` 不是当前版本的独立字段；当前 canonical 编号只有 `40800`。

## `48000` 编号更正

对 C2C 和 group 的全部非 NULL `40800` BLOB 做顶层及最多三层递归 wire 扫描：所有顶层 key 都是 `40800`/wire type 2，未发现字段号 `48000` 或其 wire key `82 b8 17`。因此外部资料中的 `48000` 应视为 `40800` 的笔误或旧封装编号。

消息段结构已经归入当前 `40800 -> MsgContent` schema；不在 `c2c_40800.proto` 中增加 `48000` 别名。
