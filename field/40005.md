# 字段 `40005` — clientSeq（客户端消息序号）

| 属性 | 值 |
|------|-----|
| 字段编号 | 40005 |
| 类型 | INTEGER |
| 所属表 | c2c_msg_table |
| 主键 | ✗ |
| 置信度 | 🔍 中（统计规律强，但未能通过协议文档直接验证） |

## 含义

**客户端侧的 16 位消息序号**：每个发送方账号各自维护一个 `uint16_t` 计数器，每发出一条消息自增 1，用于消息排序与去重。收到对方消息时，存储对方发出时的 clientSeq；发出消息时，存储己方的 clientSeq。

## 取值说明

| 值 | 含义 | 说明 |
|----|------|------|
| `0` | 序号初始值 / 缺失 | 历史数据迁移、系统消息或序号未知时为 0（约 11.8 万行，8.9%） |
| `1` ～ `65535` | 消息序号 | `uint16_t` 范围，达到 65535 后归零循环 |

## 特征

| 特征 | 结果 |

| 总行数 | 1,318,588 |

| NULL 行数 | 0 |

| 各会话起始值 | 全部从 `0` 开始 |
| 会话内时序单调性 | 74.4%（中等递增趋势，历史迁移数据存在跳跃） |
| 与 40003 相关性（Pearson） | 0.07（无关） |

## 收/发方向差异

同一会话内，收到方向（40013=0）和发出方向（40013=1）的序号模式不同：

| 方向 | 典型序号模式 | 解释 |
|------|------------|------|
| `0`（收到） | 32155 → 32156 → 32157 → 32158…（严格 +1） | 对方的 clientSeq，由对方端连续递增 |
| `1`（发出） | 0 → 4104 → 25234 → 25237 → 25239…（递增但不连续） | 己方的 clientSeq，历史迁移数据存在大幅跳跃 |

## 关联字段

| 字段 | 关系 |
|------|------|
| `40013` | 消息方向（0=收到 / 1=发出）决定 clientSeq 归属方 |
| `40002` | msgRandom（客户端随机数）；UNIQUE 索引 `(40027, 40002, 40005)` 直接证明：同一会话内 (msgRandom, clientSeq) 联合唯一，构成数据库级消息去重键 |
| `40030` | 私聊对方 QQ，clientSeq 在每个对话方内独立计数 |
| `40033` | 发送者 QQ，clientSeq 隶属于该发送者账号 |
| `40050` | 发送时间戳，与 clientSeq 在会话内大致正相关 |

## 验证方法

1. 按同一会话（`40030`）、同一发送者（`40033`）分组，按时间排序观察 40005 是否连续 +1
2. 比对收到方向（`40013=0`）的连续消息，验证 40005 是否严格 +1 递增
3. 在对端设备抓包，对比 NT 协议中 `clientSeq` 字段值与数据库存储值

## 说明

- 值 `0` 大量出现（8.94%），主要来自时间戳为 `1970-01-01` 的历史迁移记录，这些消息的序号信息可能在迁移时丢失
- 位掩码分析显示各 bit 出现率均约 50%，符合均匀分布的整数序号（非 bitmask）
- 值域精确落在 `[0, 65535]`，这是 `uint16_t` 的精确边界，可认为是类型特征的直接证据
